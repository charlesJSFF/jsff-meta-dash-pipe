**Stop condition — flagging, not deciding:** whether the six oldest diagnostic **scripts** (not just their output) should be deleted alongside their now-superseded output is a judgment call this audit isn't positioned to make. Argument for keeping: `diagnose_all_page_metrics.py` is the only script that establishes the full 80-metric candidate list (the newer `diagnose_page_metric_params.py` only re-sweeps the 37 *already-confirmed-valid* metrics, it doesn't re-derive the valid/invalid split from scratch), and `diagnose_all_ig_media_metrics.py` is the only script covering IMAGE/VIDEO/CAROUSEL_ALBUM at all (the newer `diagnose_ig_media_reels_stories.py` only covers REELS/STORY, by design — see its own docstring). Deleting the scripts would remove the ability to re-run these specific tests later, which the output-only files don't provide. Recommend a human decide per-script whether "diagnostic" (safe to prune once superseded) or "load-bearing" (keep as the reusable test) applies — this is exactly the kind of scope-ambiguous call the task brief says to flag rather than resolve.

## 2. Fold-in recommendations

Findings that currently exist **only** in diagnostic output (or only in `meta_graph_api_ref.md`, itself built from that output) and need to land in permanent, durable documentation before the underlying `.txt`/`.json` files are ever deleted:

1. **FB Page Insights range caps and rolling-window semantics** — 90-day confirmed max lookback (day/week/days_28), 182-day hard rejection (`code=100 subcode=1504016`), `period=lifetime` never returns ranged data (bare-accepted, 0 points once `since`/`until` added), `week`/`days_28` are same-cadence rolling sums ending each day — **not** calendar buckets. Source: `diagnose_page_metric_params_output.txt` (verified at lines 1-51, 170, 395). This directly affects how a transformation layer should (not) use `week`/`days_28` for monthly rollups — currently unaddressed by `PROJECT_DESCRIPTION.md`'s "Time grains" design decision, which says grains "must be pulled as separate API calls" without noting they're all daily-cadence under the hood.
2. **`since`-only query behavior**: full span from `since` to "now" in one call, no fixed ~560-day auto-page window (that was a one-data-point artifact of the anchor date used); confirmed real data back to 2023-07-18 for `page_media_view`/day; `paging.previous`/`paging.next` cursor-following is **not** a valid way to probe historical depth beyond the first hop (cursors are themselves since+until pairs and hit the same 90-day cap immediately). Source: `diagnose_since_only_pagination_output.txt` (verified in full).
3. **Legacy metric name mapping, with confidence labels**: `page_views` → `page_views_total` (confirmed, `code=100` for the old name — `diagnose_token_190_output.txt:62-71`); `page_fans` → **no confirmed successor** (`page_follows` is a plausible but unconfirmed hypothesis — no paired before/after test exists). This is currently misrepresented as resolved in `PROJECT_DESCRIPTION.md` — see Contradiction #2.
4. **`code=190` was never reproduced anywhere in this repo's diagnostics, under either token type.** Every observed failure in `diagnose_token_190_output.txt`, `diagnose_page_fans_output.txt`, `diagnose_candidate_page_metrics_output.txt`, and `diagnose_all_page_metrics_output.txt` is `code=100` (invalid metric name on v25.0), not a token-type/permission error, and the Page-token exchange changes nothing about any tested outcome. Load-bearing for the general API reference's "auth pattern" section, since it means the `/me/accounts` exchange currently exists in `auth.py` for a failure mode that has never actually been observed against this Page/token.
5. **IG media discovery gotcha**: the Graph API's `media_type` field only ever returns `IMAGE`/`VIDEO`/`CAROUSEL_ALBUM` — Reels report `media_type=VIDEO` and are only distinguishable via the separate `media_product_type` field (values seen: `FEED`, `REELS`). A script that buckets by `media_type` alone will silently miss all Reels content, which is exactly what happened once already (`diagnose_all_ig_media_metrics.py`'s original "REELS: not found" result was a false negative, corrected by `diagnose_ig_media_reels_stories.py` finding 15 REELS items in the same 50-item window). This is the single highest-value methodology fact for Phase 1 IG extraction work and needs to be in the permanent doc, not just in diagnostic output a future session may not read.
6. **Diagnostic script write pattern**: write output files via the script's own `open(path, "w", encoding="utf-8")` (the pattern already used by the 4 newest diagnostic scripts) rather than relying on shell `>` redirection — PowerShell's default UTF-16LE redirection encoding is what corrupted `diagnose_all_ig_media_metrics_output.txt`. This is a new lesson this audit surfaced; it belongs next to the existing "redact only at the output boundary" lesson already documented in `meta_graph_api_ref.md` §1.10.
7. **IG media-level results**: 7 of 10 candidate metrics succeed identically across IMAGE/VIDEO/CAROUSEL_ALBUM/REELS (`reach`, `saved`, `likes`, `comments`, `shares`, `total_interactions`, `views`); `engagement` and `video_views` are not valid Media Insights metric names at all (confirmed by the API's own enumerated "must be one of" list, which conspicuously includes Reels-only names like `ig_reels_avg_watch_time` even in IMAGE's error response — worth a callout in the metric reference as a possible non-media-type-scoped error message); `impressions` is unsupported for **every** tested media type (message text varies by type but always fails) since API v22.0. This directly contradicts `ROADMAP.md`'s current Phase 1 text — see Contradiction #3.
8. **IG account-level parameter model**: 12 of 17 working metrics require `metric_type=total_value` **and** `period=day` together, with no other period grain working for those 12; `reach`/`follower_count`/`online_followers` each behave differently again (time-series `day/week/days_28`, `day`-only, `lifetime`-only-as-snapshot respectively). The complete 28-name valid-metric enumeration (`params2.txt:17-44` in the source doc's citation, verified) is the authoritative list — no cumulative/lifetime follower-total metric exists among them. `follower_count` itself is a **daily-delta** metric (small fluctuating values, not cumulative) — this needs to be unambiguous in the metric reference given it directly contradicts an already-superseded assumption (see Contradiction below on `metric_definitions_v25.txt`).
9. **Value-shape catalog**: FB has 5 dict-valued metrics among its 37 (exact key sets documented in `meta_graph_api_ref.md` §1.7 and verified against `diagnose_candidate_page_metrics_output.txt` line 24's `page_fan_adds_by_paid_non_paid_unique` sample); IG media-level is always scalar; IG account-level has a third shape (`online_followers`, dict keyed by hour-of-day string `"0"`–`"23"`). Whoever builds the transformation layer needs this cataloged in one place, not discovered per-metric while writing parse code.
10. **Stale internal cross-references to delete once the new structure lands**: `src/extraction/fb_page_insights.py` (lines 51, 84, 122) and `auth.py` (docstring) reference `docs/relevant_api_reference.md`, which `ROADMAP.md` records as deleted in Phase 0. `diagnose_all_page_metrics.py` and `diagnose_candidate_page_metrics.py` docstrings reference `docs/meta_api_reference.md`, also deleted. Separately, `fb_page_insights.py`'s own module docstring (lines 4-5) still describes the pulled metrics as "reach, impressions, page_views_total, follower_count" — stale; the actual `DEFAULT_METRICS` constant three lines below is `page_media_view, page_total_media_view_unique, page_views_total, page_follows`. This is a code-internal doc/code mismatch, independent of any external-doc issue, and should be corrected when the reference docs are restructured (edits themselves are out of this audit's scope).
11. **Rate-limit codes** the pipeline should eventually handle: FB codes `4, 17, 32, 613` (from `diagnose_page_metric_params.py`'s detection logic, never actually triggered in a saved run) plus the already-known-deferred general code `2` and IG's `80002`. Worth listing explicitly in the general reference doc's gotchas section even though retry/backoff itself stays deferred per `.clinerules`.

## 3. Unresolved contradictions

Presented as questions needing a future testing task or a human decision — not resolved here, per scope.

### 3.1 `run_fb_page_extraction_output.csv` (and identical root-level `fb_page_insights.csv`) contain dates that postdate the file's own creation timestamp

Both files are byte-identical and were last written **2026-07-14 20:06** (`Get-ChildItem` `LastWriteTime`/`CreationTime`, both essentially the same second). They contain 13 rows spanning **2026-07-08 through 2026-07-20**. Five of those rows (07-16 through 07-20) postdate the file's own creation by 2–6 days — not physically possible for genuine Meta Graph API response data, since the API cannot return insights for days that hadn't happened yet relative to when the file was written. Separately, `scripts/run_fb_page_extraction.py`'s own code (read directly) always requests exactly a 7-day window (`until = date.today() - 1 day`, `since = until - 6 days`); a 13-row file spanning 13 calendar days is not obtainable from one run of the script as currently written, under any value of "today." `ROADMAP.md` (Phase 0, checked `[x]`) states "Confirmed: `run_fb_page_extraction.py` completed successfully... CSV output saved," and `docs/meta_graph_api_ref.md` §6 reads the file's trailing 5 zero-rows as consistent with the known finalization-lag/missing-vs-zero gaps — neither source appears to have checked whether the dates in the file are internally possible. This audit can't determine from repo contents alone whether the file was hand-assembled to illustrate the finalization-lag pattern, produced by some process outside this repo, or something else — flagging as an open question, since it bears directly on whether the ROADMAP's "confirmed successful run" claim is actually true.

### 3.2 `PROJECT_DESCRIPTION.md` Open Questions #1 and #3 are still live in the file and contradict the diagnostic output they cite as support

Read directly in the current file (lines 111-125):
- **#1** claims `diagnose_token_190.py`'s 4 calls "confirmed that token (code 190) errors no longer occur... with the current SYSTEM_USER_TOKEN + Page Access Token exchange." The script (read directly) never performs a Page-token exchange — all 4 calls use `config.system_user_token` directly — and `code=190` never appears anywhere in `diagnose_token_190_output.txt` (the one failure, Call 3 / `page_views`, is `code=100`).
- **#3** claims the Page Access Token "resolved" `page_fans` and that the raw token "returned error code 190." `diagnose_page_fans_output.txt` shows both the raw System User token (Call 1) and the exchanged Page token (Call 3) returning the **identical** `code=100` error for `page_fans` — the exchange changed nothing.

`docs/meta_graph_api_ref.md` §5.1–5.2 already identified both of these discrepancies on 2026-07-16, but per its own stated scope only flagged them without editing `PROJECT_DESCRIPTION.md` — so the incorrect "Resolved." claims are still sitting in the doc as of this audit, where a future reader would reasonably take them as settled fact.

### 3.3 `ROADMAP.md` Phase 1's `views` 400-error claim has no supporting diagnostic evidence

`ROADMAP.md` (lines 52-55) states: "views is valid for Reels/Stories but can error (400) on VIDEO+FEED and CAROUSEL_ALBUM posts, and older pre-Business-conversion posts return error subcode 2108006." Checked directly: `views` returned `SUCCESS` (200, with data) for every media type it was tested against — IMAGE, VIDEO, CAROUSEL_ALBUM (`diagnose_all_ig_media_metrics_output.txt`) and REELS (`diagnose_ig_media_reels_stories_output.txt`) — no 400 error for `views` appears in any saved output. The `subcode=2108006` claim was never tested at all (no old/non-Business-conversion post was sampled by either script). Per the task brief this is flagged, not tested further — but note it remains uncorrected in `ROADMAP.md`, and if it originated from a real prior observation rather than a carried-over assumption from the old POC repo, it may describe an edge case (old/non-Business posts) that these diagnostics simply never sampled, rather than being wrong outright.

### 3.4 The intended FB "follower total" metric for YoY cross-platform comparison is ambiguous across two docs that are each individually correct

`PROJECT_DESCRIPTION.md` (lines 70-71) lists `page_follows` as one of the pipeline's current valid/actual metrics — correct: it's confirmed `SUCCESS`, returns a genuine cumulative "Lifetime Total Follows" (`raw_response_2026-07-07_to_2026-07-13.json:131`), and is literally what `DEFAULT_METRICS` in `fb_page_insights.py` pulls today. `ROADMAP.md` (lines 36-38, added the same commit) separately states the "correct FB pairing" for matching IG's `follower_count` metric is `page_daily_follows_unique`, **not** `page_follows` — also correct, since IG's `follower_count` was independently confirmed (both by ROADMAP's own live query and by `meta_graph_api_ref.md` §4.7) to be a daily-delta metric, not a cumulative one, so pairing it with FB's cumulative `page_follows` would be a unit mismatch. Neither doc states this cumulative-vs-delta distinction explicitly, so read together they read as conflicting about "the" right follower metric when they're actually answering two different questions ("what does the pipeline pull today" vs. "what would be comparable to IG"). This borders on an architectural decision (which FB/IG metric pair, if any, belongs in a YoY follower chart) that this audit is not scoped to make — flagging per the stop-condition guidance rather than resolving it.

### 3.5 `metric_definitions_v25.txt` contains a factual claim about IG's `follower_count` that live API testing has since disproven

`metric_definitions_v25.txt` (built 2026-07-14 from a static HTML scrape of Meta's FB-side docs, before any live IG account-level testing existed) states, for `page_follows`'s "Instagram Equivalent": _"follower_count = total current followers (cumulative). This is a snapshot metric, not a delta."_ Two independent, later, live-tested sources directly contradict this: `ROADMAP.md`'s live query (June 18–July 1, 2026 window) showed daily values fluctuating in the single-to-double digits, and `diagnose_ig_account_insights_params_output.txt` (verified: `follower_count` fails for every period except `day`, and a fresh sample showed values `6, 13, 6, 9, 7, 2` across consecutive days). Per the stated recency assumption, the live-tested finding wins outright — this isn't a close call, since `metric_definitions_v25.txt`'s claim was never based on a live API call at all, only on reading Meta's own (apparently ambiguous/misleading) prose description. Listed here rather than silently "resolved" because the file itself still asserts the disproven claim and someone could read it in isolation without seeing the later correction — this is the concrete basis for the delete recommendation on `metric_definitions_v25.txt` in §1, not a separate open question.

### 3.6 `raw_response_2026-07-07_to_2026-07-13.json`'s capture date doesn't line up with its own date range under the pipeline's date logic

Lower-severity version of §3.1. The file's `since=2026-07-07`/`until=2026-07-13` range is exactly what `run_fb_page_extraction.py`'s auto-date logic would produce for `today = 2026-07-14` — but the file's own mtime is 2026-07-15 07:42, a day later. Mundane explanations exist (same-day capture saved slightly late, or a manually-specified date range unrelated to `date.today()`), so this is far less conclusive than §3.1, but it's the same category of provenance question and is noted for completeness rather than silently assumed benign.

## 4. Documentation structure recommendation

Given the project's actual goal (YoY FB + IG performance dashboard), and given that `docs/meta_graph_api_ref.md` already demonstrates a citation discipline worth preserving (cite file+line, label every claim confirmed/inferred/unknown, "suggestive not proven" for numeric spot-checks) — that discipline should carry forward into the split below, not just the specific section boundaries of the current single file.

**`docs/meta_graph_api_reference.md`** — general, platform-interaction-level reference. Covers:
- **Auth pattern**: System User token → Page Access Token exchange via `/me/accounts` (`auth.py`); documented fallback behavior; explicit note that `code=190` has never been reproduced against this Page/token in any diagnostic run to date (§2.4 above), so the exchange currently exists for an unobserved failure mode — worth knowing before anyone "fixes" it further.
- **Versioning**: v25.0 pinned; Page ID / IG User ID under test recorded once (`145245558842140`, `17841401980438718`) instead of repeated per script.
- **Pagination**: `paging.next`/`paging.previous`; `since`-only vs. `since`+`until` behavior; the explicit warning that cursor-following is not a valid historical-depth probe past the first hop.
- **Range caps by platform** (a table, not prose): FB Page Insights 90-day inferred cap (day/week/days_28 only; `lifetime` and beyond-182d unconfirmed) vs. IG account-level 30-day explicit cap vs. IG media-level N/A (no period param at all). Explicitly restate the scope-discipline warning already in the current doc: findings for one platform don't generalize to the other.
- **Rolling-window semantics**: `week`/`days_28` are same-cadence daily rolling sums, not calendar buckets — applies across the whole FB Page Insights surface.
- **Value-shape taxonomy**: scalar (default), FB's 5 dict-valued metrics, IG account's hour-keyed dict — general guidance to check shape before assuming scalar, pointing into the metric-reference files for the per-metric specifics.
- **Known systemic gaps/gotchas**: missing-vs-zero ambiguity, ~28-day finalization lag (cross-reference Contradiction §3.1 as an open item rather than a settled fact), rate-limit codes, the redaction-timing lesson (§1.10 of the current doc), the UTF-8-output-file lesson (new, §2.6 above).
- **Explicitly out of scope**: Ads Insights, Post-level metrics, breakdowns/`fields` params — restate this boundary so it isn't silently assumed covered.

**`docs/metric_reference_fb_page.md`** — one row per confirmed FB Page Insights metric (37 currently), each specifying: allowed `period` values, range-cap deviations from the platform default, value shape (scalar vs. which dict-key set), legacy name it replaced (with confidence label — confirmed vs. inferred, per Contradiction §3.2/Fold-in §2.3), and a cumulative-vs-delta tag (resolves the ambiguity in Contradiction §3.4). Source-cite every row back to `diagnose_page_metric_params_output.txt` by line, exactly as the current doc's §2 table already does — that table can likely move here close to verbatim.

**`docs/metric_reference_ig.md`** — split internally into a media-level section and an account-level section (they're structurally distinct surfaces, as the current doc's §3/§4 split already establishes and should keep).
